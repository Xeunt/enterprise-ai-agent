# Enterprise AI Document Agent

An enterprise-style agentic AI application built on AWS.

## Architecture

The solution uses:

- Amazon Bedrock Nova Lite
- AWS Lambda
- Amazon S3
- Amazon API Gateway (HTTP API)
- Amazon CloudWatch Logs
- Terraform
- GitHub Actions
- GitHub OIDC

## Purpose

The AI agent can answer questions using documents stored in Amazon S3.

The agent can decide when it needs to retrieve information from S3 before generating an answer.

## Security

This API is protected by two layers:

1. **API key authentication** - every request to `POST /ask` must include a valid
   `x-api-key` header, checked inside the Lambda function against the `API_KEY`
   environment variable (auto-generated by Terraform via `random_password`).
   Requests without a valid key receive `401 Unauthorized`.
2. **Throttling** - the API Gateway stage is rate-limited to `1 request/second`
   with a burst of `1`, to prevent abuse and control cost. Adjust
   `throttling_rate_limit` / `throttling_burst_limit` in `api_gateway.tf` if
   you need higher limits.

Access logs (caller IP, method, status code, etc.) are written to CloudWatch
Logs at `/aws/apigateway/enterprise-ai-agent-api` with a short retention
period to keep costs near zero.

Both `api_key` and `api_url` are marked as sensitive Terraform outputs, so
neither value is printed in plaintext during `terraform apply` - this
matters since GitHub Actions logs are publicly visible on a public repo.

**two things** set up in the target AWS account first. Terraform will fail
without them.

> - `logs:DescribeLogGroups`, log-delivery actions, and resource-policy

>   updating the API Gateway resources (`aws_apigatewayv2_api`,
>   `aws_apigatewayv2_route`, `aws_apigatewayv2_integration`,
>   `aws_apigatewayv2_stage`). Without it, even a no-op `terraform apply`
>   will fail with an `apigateway:GET` `AccessDeniedException` once
>   resources already exist.

### 2. Account-level CloudWatch logging role (one-time, per AWS account)

API Gateway needs a dedicated IAM role — separate from the deploy role above —
before it's allowed to push access logs to CloudWatch **at all**, account-wide.
This is a one-time setup per AWS account, not something Terraform manages
automatically here.

**Steps (console):**

1. IAM → Roles → **Create role**
2. Trusted entity type: **AWS service** → use case **API Gateway**
   (this auto-fills the correct trust policy for `apigateway.amazonaws.com`)
3. Attach the AWS-managed policy: **`AmazonAPIGatewayPushToCloudWatchLogs`**
4. Name it (e.g. `apigateway-cloudwatch-logs-role`) → Create
5. Copy the role's ARN
6. Go to **API Gateway → Settings** (account-level, not inside a specific API)
7. Paste the ARN into **CloudWatch log role ARN** → Save

> This setting can take a few minutes to propagate after saving. If you see
> `Insufficient permissions to enable logging` on `terraform apply`
> immediately after setting this up, wait 2–3 minutes and retry.

Without this step, `terraform apply` will fail on the
`aws_apigatewayv2_stage.default` resource with a permissions error, even if
the deploy policy above is correctly attached.

## Retrieving the API Key

The API key is generated automatically by Terraform (`random_password.api_key`)
and marked as a sensitive output. Retrieve it locally after a successful apply:

```bash
terraform output -raw api_key
```

**Do not** print this value in CI/CD logs, screenshots, or commit it
anywhere. If you need it inside a GitHub Actions workflow, mask it first:

```yaml
- name: Get API key
  run: |
    API_KEY=$(terraform output -raw api_key)
    echo "::add-mask::$API_KEY"
    echo "API_KEY=$API_KEY" >> "$GITHUB_ENV"
```

## Manual Testing (Personal CLI)

If you're pulling this repo fresh, or testing from a machine that hasn't run
Terraform against this project before, initialize your local CLI against the
remote state first.

> **Run all commands below from inside the `terraform/` folder** (the
> directory containing `main.tf`, `api_gateway.tf`, `lambda.tf`, etc.).
> Running `terraform output` from any other directory returns nothing —
> no error, no value, just a blank result — which looks like a broken
> command but is actually just Terraform not finding a `.tf` config or
> state in your current path.
>
> ```bash
> cd terraform
> pwd        # confirm you're in the right folder
> ls *.tf    # confirm you see main.tf, api_gateway.tf, lambda.tf, etc.
> ```

### 1. Set up your local AWS credentials

Make sure your CLI has credentials with at least read access to the state
bucket (`enterprise-ai-document-agent-tfstate`), e.g. via `aws configure`,
environment variables, or an SSO profile.

### 2. Initialize Terraform locally

```bash
terraform init
```

If you've previously initialized against a different backend/state, or see a
"Backend initialization required" error:

```bash
terraform init -reconfigure
```

### 3. Grab the API key and URL into local variables

```bash
API_KEY=$(terraform output -raw api_key)
API_URL=$(terraform output -raw api_url)
```

Sanity check the key resolved (prints length only, not the value):

```bash
echo "Key length: ${#API_KEY}"
# should print: Key length: 32
```

Avoid running `terraform output -raw api_key` directly (without capturing
it into a variable) in a shared terminal, screen share, or recording - it
prints the secret in plaintext to your terminal.

### 4. Test — valid request (expect `200`)

```bash
curl -i -X POST "${API_URL}ask" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $API_KEY" \
  -d '{"question":"Facts about the company?"}'
```

Expected: `HTTP/2 200` with a JSON body containing `question` and `answer`
(no `document` field — internal S3 paths are not exposed in responses).

### 5. Test — missing API key (expect `401`)

```bash
curl -i -X POST "${API_URL}ask" \
  -H "Content-Type: application/json" \
  -d '{"question":"Facts about the company?"}'
```

Expected: `HTTP/2 401` with `{"error": "Unauthorized"}`.

### 6. Test — wrong API key (expect `401`)

```bash
curl -i -X POST "${API_URL}ask" \
  -H "Content-Type: application/json" \
  -H "x-api-key: wrong-key-here" \
  -d '{"question":"Facts about the company?"}'
```

Expected: same `401` response as above.

### 7. Test — throttling (expect a mix of `200` and `429`)

The stage is limited to 1 request/second with a burst of 1. Sequential curl
calls usually won't trigger this (each request naturally takes 1–3+ seconds
end-to-end due to two Bedrock calls), so fire a larger batch concurrently to
actually observe throttling:

```bash
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "Request $i: %{http_code}\n" \
    -X POST "${API_URL}ask" \
    -H "Content-Type: application/json" \
    -H "x-api-key: $API_KEY" \
    -d '{"question":"Facts about the company?"}' &
done
wait
```

Expected: some requests return `200`, others return `429 Too Many Requests`.

> Note: this fires up to 20 real Bedrock invocations if not throttled —
> use sparingly to avoid unnecessary cost.

### 8. Clean up variables (optional)

```bash
unset API_KEY API_URL
```

> Note: `$API_KEY` and `$API_URL` are only set for your current terminal
> session. If you open a new terminal tab/window, or your session resets,
> you'll need to `cd` back into the `terraform/` folder and re-run step 3
> before testing again — otherwise curl will fail with something like
> `curl: (6) Could not resolve host: ask` because the variable was empty.

## Cost Notes

This stack is designed to run at near-zero cost for a single-tester/dev setup:

- API Gateway (HTTP API) and Lambda: pay-per-request, no idle cost.
- CloudWatch Logs: 1-day retention on API Gateway access logs.
- S3: negligible storage for small text documents.
- Bedrock Nova Lite: pay-per-invocation, two calls per `/ask` request
  (classification + answer generation).

No resources in this stack incur cost while idle/undeployed between test
sessions, so it's not necessary to `terraform destroy` between uses.
